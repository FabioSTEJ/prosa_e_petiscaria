========================================================
  PROSA E PETISCARIA — GUIA DE DEPLOY EM PRODUCAO
========================================================

PRE-REQUISITOS
--------------
- Docker instalado na maquina/servidor
- Docker Compose instalado
- Porta 5500 liberada no firewall

Para verificar se estao instalados, execute:
  docker --version
  docker compose version


PASSO 1 — COPIAR O PROJETO PARA O SERVIDOR
-------------------------------------------
Copie a pasta do projeto para o servidor (via pendrive, FTP, SCP, etc.).
Certifique-se de que os seguintes arquivos estejam presentes na raiz:

  Dockerfile
  docker-compose.yml
  entrypoint.sh
  run.py
  requirements.txt
  app/
  scripts/

NAO e necessario copiar:
  - venv/
  - .env
  - comandas.db
  - __pycache__/


PASSO 2 — CONFIGURAR A CHAVE SECRETA
--------------------------------------
Crie um arquivo .env na raiz do projeto (baseado no .env.example) e
defina SECRET_KEY com uma sequencia de caracteres aleatorios e segura.
O container le essa variavel automaticamente via docker-compose.yml.

  Exemplo (.env):
    SECRET_KEY=x7Kp!mQ2@vLz93nWdYr6sTuA

Se SECRET_KEY nao estiver definida, a aplicacao falha ao iniciar com
uma mensagem de erro clara. Nunca use uma chave fixa no codigo.


PASSO 3 — CONSTRUIR E SUBIR O CONTAINER
-----------------------------------------
Na pasta raiz do projeto, execute:

  docker compose up --build -d

  --build   -> reconstroi a imagem com o codigo atual
  -d        -> roda em segundo plano (modo daemon)

Na PRIMEIRA vez que rodar, o sistema vai:
  1. Instalar as dependencias Python
  2. Criar o banco de dados vazio
  3. Criar o usuario admin automaticamente
  4. Registrar que o seed ja foi executado (nao repete nos proximos starts)
  5. Iniciar o servidor


PASSO 4 — VERIFICAR SE ESTA RODANDO
--------------------------------------
Execute:

  docker compose ps

Deve aparecer o container com STATUS "Up".

Para ver os logs em tempo real:

  docker compose logs -f


PASSO 5 — ACESSAR O SITE
--------------------------
Abra o navegador e acesse:

  http://<IP-DO-SERVIDOR>:5500

Se estiver rodando na propria maquina:

  http://localhost:5500


PASSO 6 — PRIMEIRO LOGIN DO ADMIN
------------------------------------
Na tela de login, use as credenciais iniciais:

  Usuario: admin
  Senha:   123

O sistema vai exigir a troca de senha no primeiro acesso.
Escolha uma senha forte e guarde em local seguro.


========================================================
  COMANDOS UTEIS NO DIA A DIA
========================================================

LIGAR o container (inicio do dia):
  docker compose start

DESLIGAR o container (fim do dia):
  docker compose stop

REINICIAR:
  docker compose restart

VER LOGS:
  docker compose logs -f

RECRIAR O ADMIN MANUALMENTE (caso tenha sido deletado):
  docker exec -it prosa_e_petiscaria-web-1 python scripts/seed_admin.py
  (apos isso, login: admin / 123 e o sistema pede troca de senha)

ATUALIZAR O SITE (nova versao do codigo):
  git pull origin main
  docker compose build
  docker compose run --rm web python scripts/migrar_tudo.py
  docker compose up -d

  IMPORTANTE: nunca pule o passo do "migrar_tudo.py". Sempre que uma
  atualizacao adiciona um campo/tabela nova, o banco de dados existente
  (com os pedidos, mesas e vendas ja cadastrados) precisa desse passo pra
  ganhar as colunas novas SEM perder nenhum dado. Reiniciar direto com
  "docker compose up --build -d" (sem migrar antes) pode derrubar o site
  com erro de "coluna nao existe".

  O migrar_tudo.py roda TODOS os scripts scripts/migrar_*.py em sequencia.
  Cada um deles verifica sozinho se ja foi aplicado e pula se sim — por
  isso e seguro rodar esse comando em toda atualizacao, mesmo que nenhuma
  migracao nova exista dessa vez (nesse caso ele so imprime "nada a migrar"
  pra cada um e nao mexe em nada).


========================================================
  OBSERVACOES IMPORTANTES
========================================================

- O banco de dados fica salvo em um volume Docker chamado "db_data".
  Ele NAO e apagado ao desligar ou reiniciar o container.
  So e apagado se voce executar: docker compose down -v  (CUIDADO)

- O arquivo .seeded dentro do volume impede que o admin seja
  recriado automaticamente a cada start. Se precisar recriar
  o admin, use o comando manual descrito acima.

- Para acessar de outros dispositivos na mesma rede (celulares,
  tablets, outros computadores), use o IP local do servidor:
  http://192.168.x.x:5500

- NAO exponha a porta 5500 pra internet (sem port forwarding no roteador).
  O acesso deve ficar restrito a rede local do estabelecimento.

========================================================
  PARA QUEM (OU QUAL IA) FOR ESCREVER UMA MIGRACAO NOVA
========================================================

Sempre que um model em app/core/models/ ganhar uma coluna/tabela nova E
o banco de producao ja tiver dados reais, db.create_all() NAO alcanca essa
tabela (so cria tabelas que ainda nao existem, nunca altera uma existente).
E preciso escrever um script de migracao manual. Regras pra nao repetir os
bugs que ja apareceram aqui:

1. Nome do arquivo: scripts/migrar_<algo_descritivo>.py — o migrar_tudo.py
   descobre e roda automaticamente qualquer scripts/migrar_*.py.

2. IDEMPOTENTE DE VERDADE: verifique o estado real do banco antes de mudar
   qualquer coisa (ex.: PRAGMA table_info pra checar se a coluna ja existe,
   ou o flag "notnull" real de uma coluna). NUNCA confie em heuristica de
   texto tipo "'coluna' in sql_da_tabela" — o nome da coluna aparece no SQL
   mesmo quando ela ja esta do jeito certo, entao esse tipo de checagem
   sempre da "precisa migrar" e a migracao roda toda vez sem necessidade.

3. Se a migracao recriar uma tabela (necessario pra mudar nullable/tipo,
   já que SQLite não suporta ALTER COLUMN): a lista de colunas do
   CREATE TABLE ... _new tem que bater EXATAMENTE com o schema atual do
   model, incluindo colunas adicionadas por migracoes anteriores. Uma
   lista desatualizada apaga essas colunas (e os dados nelas) em silencio.
   Prefira reler PRAGMA table_info(tabela_atual) e montar a copia de dados
   dinamicamente em vez de hardcodar os nomes das colunas.

4. Backup antes de qualquer alteracao destrutiva, com nome de arquivo
   UNICO por script (ex.: comandas.db.backup.migrar_xyz) — se dois scripts
   usarem o mesmo nome de backup, o segundo sobrescreve o backup do
   primeiro e ele deixa de servir pra restaurar.

5. Teste rodando scripts/migrar_tudo.py duas vezes seguidas contra uma
   copia do banco antes de considerar pronto. A segunda vez tem que
   imprimir "nada a migrar" pra tudo, sem recriar nenhuma tabela.
